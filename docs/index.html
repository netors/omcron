Theme

Scheduled jobs that ask before they act

Omarchy has reminders, which are one-shot and inert, and Arch has cron, which runs whatever you gave it whether or not you are ready. omcron is the middle: a repeating job that either runs on its own, or posts a notification asking permission first — using the same toast the reminders use.

Why it exists

The gap between a reminder and a cron job

A reminder tells you to do something and then forgets about it; you still run the command yourself. A cron job runs the command but never asks, which is fine for a backup and wrong for anything that changes your tools, touches the network, or interrupts what you are doing.

The motivating case: a package manager holds a release behind a 24-hour age gate. You want the upgrade attempted every weekday morning, but you want to say yes first, because sometimes you are mid-task and an upgrade is the last thing you want. A reminder would nag you into running it by hand. A cron job would run it behind your back. omcron posts a notification you click to approve.

Install

Two commands, and why it is two rather than one

omarchy plugin add https://github.com/netors/omcron.git --enable --yes
~/.config/omarchy/plugins/netors.omcron/install.sh

The first installs the bar widget; the second puts the omcron command on your PATH. It is deliberately two steps: omarchy plugin add never runs code from a plugin — no install hooks, no sudo — so nothing can put a binary on your PATH on your behalf.

The directory is named from the plugin id

A plugin is cloned to ~/.config/omarchy/plugins/<manifest id>/, not to the repo name. So the repo netors/omcron installs to netors.omcron/. Every path in this document uses the id.

Place the widget wherever suits you — beside the indicator cluster is a reasonable default:

omarchy bar put netors.omcron --section center --after omarchy.indicators

CLI only

The command works without the widget, and without Omarchy, given a systemd user instance:

git clone https://github.com/netors/omcron.git && cd omcron && ./install.sh

Set OMCRON_NOTIFY and OMCRON_PICKER to point at notify-send, fuzzel or rofi if Omarchy's own tools are not present.

Updating

omarchy plugin update netors.omcron

This is a fast-forward pull of the repo, re-validated afterwards and rolled back automatically if validation fails. Because the CLI is symlinked out of the plugin directory by install.sh, the same command updates the command and the widget together.

Jobs and schedules

One JSON file and one timer pair per job

A job is a name, a schedule, a command, and a mode. The command is stored as an argv array, never a string, so an argument containing spaces stays one argument and can never be re-parsed into a command:

omcron add mise-claude --at 'Mon..Fri 09:30' --ask \
  --desc 'Upgrade Claude' --run mise upgrade claude

Use --shell '<line>' instead when you genuinely want pipes, globs or redirection. --run must come last, because it consumes the rest of the line.

Schedules are systemd OnCalendar expressions, not five-field cron. There is no translation layer, and every schedule is validated with systemd-analyze calendar at add time — so a typo is rejected immediately rather than silently never firing.

ExpressionMeans
dailyevery day at 00:00
hourlyevery hour on the hour
Mon..Fri 09:30weekdays at 09:30
*:0/15every 15 minutes
Sun *-*-* 04:00Sundays at 04:00
2026-08-26 15:33once, at that moment

The two modes

The whole point of the tool

Runs on schedule, tells you afterwards. The timer fires, the command runs, its output is appended to the job log, and you get a toast with the outcome.

Success is a low-urgency toast that clears itself. Failure is critical, so it stays until you deal with it, and carries the exit status. Both are clickable and open the log.

Right for backups, cleanups, syncs — anything whose failure you want to hear about but whose success needs no permission.

Posts a request instead of running. Nothing executes until you click. The toast is critical so it never times out, and because Omarchy stores a toast's click action as data rather than as a libnotify action, an unanswered request stays clickable in notification history — even across a shell restart.

Clicking opens a picker with five choices. Ignoring the request entirely means the job simply does not run; the next scheduled fire supersedes it.

Right for upgrades, anything that interrupts, anything you would want to decline while mid-task.

The approval flow

And the token that keeps it honest

1

The timer fires

omcron fire <name> runs as a oneshot service. An auto job stops here and just runs.

2

A one-shot token is minted

An ask job writes $XDG_RUNTIME_DIR/omcron/pending/<name>.json holding a fresh token. One pending token per job, so a new fire replaces an unanswered older one rather than stacking up.

3

The request is posted

A critical toast whose click action is omcron respond <name> <token>, carried as an argv vector so no part of it is ever shell-interpreted.

4

The click is validated

respond fails closed: it proceeds only if the token it was given is the current pending token. No pending file, or a different one, and it refuses. This is what stops a stale toast from running the job days later.

5

You choose

The picker opens. Only a real decision spends the token.

Run now

Executes the command, logs it, posts the outcome.

token spent

Skip this one

Declines this occurrence. The recurrence is untouched.

token spent

Snooze 15m / 1h

Arms a transient timer to re-post later. The schedule itself does not move.

token spent, re-minted later

Open the log

Reading is not deciding, so the request survives.

token kept

Esc / dismiss

Re-posts the same request so an accidental dismissal costs nothing.

token kept

Bar widget

All logic in the CLI, none in the QML

The widget is deliberately thin: the CLI emits a JSON envelope and the QML only renders it. That split keeps every decision somewhere testable without a compositor.

$ omcron list --json
{"count":1,"waiting":0,"active":true,
 "tooltip":"1 job scheduled\nUpgrade Claude  Thu 27 Aug 09:30  (asks)",
 "jobs":[ ... ]}

A timer glyph when jobs are scheduled; an alert glyph in the urgent colour when one is waiting on you. Hovering lists every job and its next run. Clicking answers the oldest outstanding request, or posts a summary when there is none.

SettingDefaultDoes
showWhenEmptytrueStay on the bar, dimmed, when there are no jobs
attentionOnlyfalseHide unless something is waiting. Overrides the above
refreshIntervalSec60How often to re-read state. CLI changes refresh it immediately regardless

Why a standalone widget and not an indicator

This is the part worth reading if you are writing an Omarchy plugin of your own.

The obvious home for this is Omarchy's Indicators cluster, beside the reminder bell and the do-not-disturb icon. You cannot get there. Indicator discovery is one hardcoded line in Indicators.qml:

source: Qt.resolvedUrl("../indicators/" + indicatorSlot.indicatorId + ".qml")

That is the entire mechanism. There is no search path, no user override directory, no indicator plugin kind, and no registry API — BarWidgetRegistry keys on whole widgets by manifest id, and nothing analogous exists one level down. The manifest's items list is a hardcoded array of the six built-ins.

Upstream's sanctioned answer is omarchy plugin clone omarchy.indicators, which copies the whole widget into your plugins directory and rewrites its loader paths. That works, and this tool shipped that way at first. But a clone is a fork: every user who installed it would stop receiving upstream changes to a core bar widget, forever, in exchange for one icon.

A standalone bar widget costs one thing — it sits beside the cluster rather than inside it, and does not share the cluster's hover-reveal — and buys first-class plugin lifecycle, omarchy plugin update, a generated settings UI, and placement anywhere on the bar. That trade is not close.

Shell findings worth knowing

Two behaviours of the Omarchy shell that are not guessable, and that any adopter will hit

Toast lifetime is decided by urgency, not by -t

In Service.qml, durationFor() gives low 5 s and normal 8 s, both capped at 30 s even if you pass a longer -t. Only -u critical returns duration 0, meaning it stays until acted on.

Any notification that asks for a decision must be critical. The first version of this tool used normal and approval requests silently evaporated after eight seconds.

Click actions are persisted as data

omarchy-notification-send --exec stores the argv vector in the omarchy-exec-argv hint rather than registering a libnotify action, so a toast stays clickable from notification history across a shell restart (NotificationLogic.js).

Excellent for recoverability — a missed approval is not lost. But it means a click-to-act design must validate at click time: without that, a request from days ago is still armed. Hence the one-shot token.

Related: --exec takes the command as separate words and explicitly refuses a single word containing spaces, so an untrusted value can only ever be one argument. omcron mirrors that posture for --run.

Design decisions

The ones an adopter would otherwise have to rediscover

Named omcron, not omarchy-cron

/usr/share/omarchy/bin comes first on PATH, ahead of ~/.local/bin. If upstream ever shipped a command called omarchy-cron, it would silently shadow this one and every job would stop working with no visible cause. A distinct name is immune.

The trade-off: it cannot be reached as omarchy cron. The dispatcher resolves subcommands by scanning its own package bin directory (OMARCHY_BIN_DIR, derived from the script's own location), which a user-installed command can never join without editing package-owned files. An upstream version would not have this constraint — see below.

PATH is captured at add time

A systemd user service gets a minimal environment. Without help, a job calling mise, or anything in ~/.local/bin, fails with a bare command not found at 3 am. So add records the current PATH into the job and bakes it into the unit as Environment=PATH=….

Consequence

The job inherits the PATH of the shell that created it, frozen. Re-add or edit a job after a significant toolchain change. An upstream version might prefer resolving the binary to an absolute path at add time instead.

OnCalendar, not cron syntax

Passing schedules straight through to systemd means no translation layer to get wrong, free validation via systemd-analyze calendar, and access to expressions cron cannot express. The cost is that */15 * * * * is not accepted; write *:0/15.

Failing closed everywhere

Unknown option, unparseable schedule, missing job, ambiguous --run, stale token: all refuse rather than guess. The one place this is user-visible is that ignoring a request means the job does not run. There is no escalation and no auto-run fallback, which is the correct default for a consent gate but does mean an ask job can go a long time without running if you are away.

What is tested

And, more usefully, what is not

110 automated assertions run on every push: argument handling, unit-file generation, the list --json envelope the widget consumes, run and failure logging, the full job lifecycle, doctor, and the approval gate.

The approval gate is the interesting one. Every bug this tool has had lived there, and none was reachable without a human clicking a notification and choosing from a picker. The fix was to make both external interactions injectable — OMCRON_NOTIFY and OMCRON_PICKER — so a stub can stand in for them. Those same seams let you run omcron with notify-send and fuzzel instead, which is a nicer justification than "for the tests".

Three bugs found by hand-testing, all in the consent gate

1. Requests expired after 8 seconds. They were sent at normal urgency. Only critical returns duration 0 in the shell's durationFor() — a decision request must never time out.

2. The token guard failed open. Written as if [[ -n $token && -f $pending ]], so once any click removed the pending file, every stale toast fell straight through to the picker. Since click actions are persisted as data and outlive their request, an approval from days ago stayed armed. Now a missing pending file is a refusal.

3. Esc silently discarded the occurrence. Dismissing the picker consumed the token, making an accidental keypress less recoverable than ignoring the toast entirely. It now re-posts the same token.

All three are locked in as regression tests.

The honest gap

The stubbed picker asserts the labels omcron sends, not that omarchy-menu-select returns them unchanged. If that tool's return format ever changes, all five branches break and CI stays green. Likewise none of Omarchy's interfaces are versioned, and QML is never linted — qmllint cannot resolve qs.Ui outside the shell tree.

test/MANUAL.md in the repo is the checklist for everything a runner cannot prove: a toast actually persisting, a timer actually firing, the widget actually rendering. It is meant to be walked before tagging a release and after any Omarchy upgrade.

If Omarchy adopted this

What would change in a first-party version

  • It becomes omarchy-cron, living in the package bin directory, and the naming constraint above disappears — omarchy cron add … would route automatically via the omarchy:summary / omarchy:group metadata comments the dispatcher scans.
  • The bar presence could become a real indicator inside the stock cluster, which today is impossible for third parties — see why a standalone widget. Better still would be an extension point so any plugin can contribute an indicator without forking the widget; that would be worth more to the ecosystem than adopting this tool.
  • An interactive add flow, the way omarchy reminder -i summons omarchy.reminders — a small Quickshell panel for name, schedule and mode beats remembering OnCalendar syntax.
  • Approval buttons in the toast itself, if the notification surface grows multi-action support, would remove the picker hop. The token model already supports it: each action just carries the same argv with a different verb.
  • A migration for anyone who installed the user-space version, moving ~/.config/omcron/jobs/ and rewriting unit files under the new name.
Scope this deliberately excludes

No per-job environment beyond PATH, no dependency ordering between jobs, no run history beyond an appended log, no calendar UI, and no escalation policy for unanswered requests. Each is a reasonable addition; none is needed for the tool to be useful.
